## 测试配置

- 硬件：NVIDIA L4；所有已记录结果均使用相同的 TensorRT 10.7.0 环境。
- 输入：静态 `1x3x224x224` FP16，输出 `1x1000`。

## 实验执行指令

以下仅列出三类实验各一条样例；将命令中的 `50` 同步替换为 `15` 或 `100`，即可运行相同类型的不同 schemes 实验。

### 1. direct AutoTune

```bash
mkdir -p autotune_output/vit/direct-fp16-s50 model_home/vit/autotune-logs/direct

CUDA_VISIBLE_DEVICES=0 /root/.conda/envs/modelopt/bin/python -m modelopt.onnx.quantization.autotune \
  --onnx_path ./model_home/vit/vit.fp16.onnx \
  --output_dir ./autotune_output/vit/direct-fp16-s50 \
  --timing_cache ./autotune_output/vit/direct-fp16-s50/trt_timing.cache \
  --quant_type int8 \
  --schemes_per_region 50 \
  --warmup_runs 10 \
  --timing_runs 50 \
  > ./model_home/vit/autotune-logs/direct/direct-fp16-s50.log 2>&1
```

### 2. Q/DQ baseline AutoTune

```bash
mkdir -p autotune_output/vit/qda-s50 model_home/vit/autotune-logs/qda

CUDA_VISIBLE_DEVICES=0 /root/.conda/envs/modelopt/bin/python -m modelopt.onnx.quantization.autotune \
  --onnx_path ./model_home/vit/vit.fp16.onnx \
  --qdq_baseline ./model_home/vit/vit.int8.onnx \
  --output_dir ./autotune_output/vit/qda-s50 \
  --timing_cache ./autotune_output/vit/qda-s50/trt_timing.cache \
  --quant_type int8 \
  --schemes_per_region 50 \
  --warmup_runs 10 \
  --timing_runs 50 \
  > ./model_home/vit/autotune-logs/qda/qda-s50.log 2>&1
```

### 3. integrated API AutoTune

```bash
mkdir -p autotune_output/vit/integrated-s50 model_home/vit/autotune-logs/integrated
```

# ModelOpt Integrated AutoTune 加速下降原因分析

## 1. 实验现象

以 ViT INT8 量化为例，不同 AutoTune 流程得到的 TensorRT 加速比如下：

| 模型                    | 配置                                            |    SpeedUp |
| --------------------- | --------------------------------------------- | ---------: |
| vit.fp16              | FP16 baseline                                 |      1.00× |
| vit.int8              | 标准 INT8 PTQ                                   |      1.37× |
| direct AutoTune s=50  | Direct AutoTune 搜索输出                          | 1.38～1.41× |
| integrated-search-s50 | Integrated 内部 AutoTune `optimized_final.onnx` |  **1.41×** |
| integrated-autotune50 | Integrated API 最终校准模型                         |  **1.23×** |

最关键的现象是：

```text
Integrated AutoTune 搜索输出：1.41×
                ↓
       INT8 Calibration / ORT
                ↓
Integrated 最终输出：1.23×
```

因此可以基本排除 **AutoTune 搜索能力不足**。Integrated API 内部的 AutoTune 已经找到了性能很好的 Q/DQ placement，主要性能损失发生在 **AutoTune 结果传递到最终 INT8 PTQ 模型的阶段**。

---

## 2. Integrated API 的实际处理流程

Integrated API 并不是直接对 AutoTune 生成的 `optimized_final.onnx` 做 calibration。

实际流程更接近：

```text
FP16 ONNX
   ↓
AutoTune
   ↓
得到精确 Q/DQ insertion points
   ↓
转换为 ORT quantization config
   ├─ nodes_to_quantize
   ├─ no_quantize_inputs
   └─ op_types_needing_output_quant
   ↓
ONNX Runtime quantize_static()
   ↓
重新生成 Q/DQ
   ↓
Calibration
   ↓
最终 INT8 ONNX
```

因此中间存在一次：

```text
精确 edge-level Q/DQ placement
                ↓
         ORT 配置表示
                ↓
       ORT 重新构造 Q/DQ
```

实验表明，这次转换没有完全保持 AutoTune 原本找到的 Q/DQ topology。

---

## 3. Q/DQ 拓扑对比结果

对 `integrated-search-s50` 与最终 `integrated-autotune50` 进行比较：

| 指标               | AutoTune Search | Final Calibrated |      变化 |
| ---------------- | --------------: | ---------------: | ------: |
| 总节点数             |             930 |              906 |     -24 |
| QuantizeLinear   |             195 |              183 |     -12 |
| DequantizeLinear |             195 |              183 |     -12 |
| Weight Q/DQ      |              73 |               97 | **+24** |
| Activation Q/DQ  |             122 |               86 | **-36** |

这说明最终模型并不是简单地：

```text
保持原来的 Q/DQ
+
修改 calibration scale
```

而是实际上**重新改变了量化边界**。

---

## 4. 主要拓扑变化

### 4.1 新增 36 个 Add 输入 Q/DQ

最终模型新增了 36 个类似：

```text
onnx::Add_xxx
      ↓
     Q/DQ
      ↓
Linear / FC 后的 Add
```

它们规律非常明显：

```text
每个 Transformer Block：

attn/proj/Add
mlp/fc1/Add
mlp/fc2/Add

3 × 12 Block = 36
```

从 tensor 名称、数量以及网络结构来看，这些输入高度疑似 Linear 层对应的 bias initializer。

这意味着搜索阶段原本可能是：

```text
bias ─────────┐
              Add
activation-QDQ┘
```

最终 ORT 模型却可能变成：

```text
bias ─ Q/DQ ─┐
             Add
activation ──┘
```

这会改变 TensorRT 对 Linear / MatMul + Bias 的 precision propagation、fusion 和 tactic 选择。

它也是目前最值得怀疑的性能下降来源之一。

---

### 4.2 11 个 `Add → Gelu` Q/DQ 被删除

AutoTune 搜索模型中存在：

```text
FC1
 ↓
Add
 ↓
Q/DQ
 ↓
Gelu
```

最终 calibrated 模型中，这些边界基本全部消失。

这非常重要，因为 ViT 的 MLP 主路径就是：

```text
FC1 → GELU → FC2
```

AutoTune 是根据 TensorRT 实际 latency 主动选择了这些 Q/DQ placement，因此删除它们意味着：

> ORT 最终生成的量化图没有完整保留 AutoTune 在关键 MLP 路径上找到的最优 precision boundary。

这很可能直接导致 TensorRT fusion、INT8 kernel 或 reformat 路径发生改变。

---

### 4.3 Attention 中部分 Q/DQ 被删除

最终模型还删除了：

```text
24 × Div → Sqrt
12 × Cast → Sqrt
```

这些变化说明 attention 子图的量化边界也发生了明显变化。

不过相比 MatMul / Add / GELU 主计算路径，这些 Sqrt/Div 节点本身计算量较小，因此目前认为它们更可能是次要影响因素。

---

## 5. 为什么搜索模型快，而最终模型慢？

综合目前实验，可以得到下面的解释：

```text
AutoTune
   ↓
根据 TensorRT latency
找到高性能 Q/DQ placement
   ↓
1.41×
```

但是 Integrated API 随后执行：

```text
Q/DQ insertion points
      ↓
转换为 ORT node/op 配置
      ↓
ORT quantize_static()
      ↓
重新构造 Q/DQ topology
```

这一过程中部分精确的 edge-level placement 信息发生改变：

```text
+ 36 个 Add/bias QDQ

- 11 个 Add→Gelu QDQ

- 36 个 attention Sqrt 附近 QDQ

- 12 个 LayerNorm bias QDQ
```

最终导致：

```text
AutoTune 搜到的 TensorRT 最优图
            ≠
最终 Calibration 后的 Q/DQ 图
```

所以最终 TensorRT engine 无法保留 AutoTune 搜索阶段得到的全部性能收益。

---

## 6. 为什么认为不是 Calibration 本身导致？

标准 PTQ 模型已经可以达到：

```text
vit.int8 = 1.37×
```

说明：

```text
真实 calibration
+
INT8 Q/DQ
```

本身并不会天然导致性能只有 1.22×。

同时 Integrated 内部搜索模型可以达到：

```text
1.41×
```

因此最符合当前实验结果的解释不是：

```text
Calibration scale 导致性能下降
```

而是：

```text
AutoTune placement
        ↓
ORT reconstruction
        ↓
Q/DQ topology 被改变
        ↓
TensorRT execution plan 发生变化
        ↓
1.41× → 1.23×
```

---

## 7. 当前结论

目前可以得到三个主要结论：

1. **Integrated API 的 AutoTune 搜索本身是有效的。**
   `integrated-search-s50` 已经达到 1.41×，与 Direct AutoTune 的最佳结果基本一致。

2. **性能损失主要发生在 AutoTune → ORT INT8 Calibration 的 handoff 阶段。**
   最终模型的 Q/DQ topology 与搜索模型存在明显差异，而不是单纯修改 scale。

3. **最值得怀疑的是 Linear/Add bias Q/DQ 增加以及 MLP `Add→Gelu` placement 丢失。**
   这些变化位于 ViT 的主要 GEMM/MLP 路径，更容易改变 TensorRT 的 fusion、precision region、reformat 和 tactic 选择。

因此，目前可以将 Integrated API 加速下降概括为：

> **Integrated AutoTune 找到了较优的 TensorRT Q/DQ placement，但在后续将 placement 转换为 ONNX Runtime PTQ 配置并重新生成 calibrated Q/DQ 模型时，部分 edge-level placement 信息没有被完全保持，使最终 TensorRT engine 的执行拓扑偏离搜索阶段的最优方案，从而导致加速比由约 1.41× 下降到约 1.23×。**

后续最值得做的验证是分别恢复/删除 `Add bias Q/DQ` 和 `Add→Gelu Q/DQ`，做单独的 TensorRT latency 消融，从而确定具体是哪一类 topology change 贡献了主要性能下降。
