# 08.11 AutoTune 审计报告

## 1. 审计结论

`quantize(..., autotune=True)` 当前并不是“在普通 PTQ 结果上继续优化”，而是切换到一套独立的、随机的 QDQ 放置搜索流程。

这套流程存在以下关键问题：

1. 普通 PTQ 模型没有被作为 AutoTune 的性能基线或候选方案。
2. `--autotune_qdq_baseline` 的 QDQ warm start 实际导入失败，所有缓存 scheme 都变成了零 QDQ 点。
3. 开启 AutoTune 后，会绕过普通 PTQ 中 TensorRT/compiler-friendly 的节点选择和融合分区逻辑。
4. 搜索得到的精确 edge-level QDQ 拓扑，会被压缩成 node-level ORT 配置，再由 ORT 从原始模型重新生成 QDQ，导致拓扑变化。
5. 搜索模型和最终模型使用不同的 scale、数据精度以及部分 TensorRT builder 配置。
6. AutoTune 没有最终性能回退机制，搜索结果比普通 PTQ 慢时仍会被输出。

因此，AutoTune 比不开启更慢并非单一问题，而是“搜索基线失效、搜索空间退化、QDQ 交接有损、搜索条件不一致、缺少回退保护”共同导致的结果。

其中，已有报告提出的“AutoTune QDQ 模式无法完整传递给最终 quantizer”是正确结论，但它主要解释 ViT 旧 integrated 实验，不能单独解释 ResNet50 接近两倍的性能回退。

## 3. 实验结果对比

| 模型/方案 | 普通 PTQ P50 | AutoTune 搜索模型 | AutoTune 最终模型 | 观察 |
|---|---:|---:|---:|---|
| ViT 旧 integrated-s50 | 0.977 ms | 0.949 ms | 1.085 ms | 搜索模型较快，转换后的最终模型较慢，QDQ 交接损失是主要因素 |
| ViT QDQ baseline s50 | 0.977 ms | 内部约 0.92 ms | 1.070 ms | QDQ 交接明显改善，但最终仍慢约 9.5% |
| ViT QDQ baseline s100 | 0.977 ms | 内部约 0.89 ms | 1.011 ms | 搜索次数增加后接近普通 PTQ，但仍未稳定胜出 |
| ResNet50 integrated-QDQ s50 | 0.299 ms | 0.761 ms | 0.598 ms | 最终模型比搜索模型快，但仍比普通 PTQ 慢约 100% |

### 3.1 ViT 旧 integrated 实验

旧 ViT integrated-s50 的搜索模型约为 `0.949 ms`，最终模型约为 `1.085 ms`。搜索模型本身能够超过普通 PTQ，但转换为最终 ORT 量化模型后性能下降。

对应的 QDQ 统计为：

- 搜索模型：195 个 Q、195 个 DQ
- 最终模型：183 个 Q、183 个 DQ
- 搜索模型 activation Q：122
- 最终模型 activation Q：86

其中大量 Add 到 GELU、Sqrt 等节点之间的 activation QDQ 在最终模型中消失。该实验支持既有报告提出的结论：精确 insertion point 无法完整传给最终 quantizer。

### 3.2 ViT QDQ baseline 实验

在新的 integrated-QDQ s50 中：

- 搜索模型：218 个 Q，其中 97 个 weight、121 个 activation
- 最终模型：217 个 Q，其中 97 个 weight、120 个 activation

从数量上看，activation QDQ 基本保留。因此，新实验中的约 9.5% 回退不能再简单归因于“最终模型少了很多 activation QDQ”。

进一步比较 initializer QDQ 后发现：

- 搜索和最终模型共同保留了部分 MatMul weight 和 Add constant。
- 搜索模型中的 36 个 LayerNormalization 参数 QDQ 在最终模型中消失。
- 最终模型增加了 12 个 MatMul weight QDQ 和约 24 个 Add bias/constant QDQ。

也就是说，QDQ 总数接近并不代表量化语义相同。QDQ 从 LayerNorm 参数转移到了 MatMul weight 和 Add bias，仍可能改变 TensorRT 的 MatMul+Add/GEMM、残差及 reformat fusion。

### 3.3 ResNet50 实验

ResNet50 的现象证明 QDQ handoff 不是全部原因：

- 普通 PTQ：`0.299 ms`
- AutoTune 搜索模型 s50：`0.761 ms`
- AutoTune 最终模型 s50：`0.598 ms`

最终模型相对于搜索模型反而更快，因此 ResNet 的主要问题发生在 AutoTune 搜索策略本身，而不是搜索模型向最终模型转换时。

普通 PTQ 与 AutoTune s50 的主要拓扑差异为：

- 普通 PTQ：53 个 Conv weight QDQ，约 54 个 activation QDQ
- AutoTune 搜索模型：33 个 Conv weight、1 个 Gemm weight、52 个 activation QDQ
- AutoTune 最终模型：35 个 Conv weight、1 个 Gemm weight、64 个 activation QDQ

AutoTune 最终模型缺少普通 PTQ 中 18 个 Conv weight 的 INT8 路径。这些节点主要是 ResNet bottleneck 中的 1×1 reduction/projection Conv。

同时：

- 普通 PTQ engine 约为 28.3 MiB
- AutoTune s50 engine 约为 33.5 MiB

更大的 engine 和明显更慢的执行时间共同表明，AutoTune 没有保住普通 PTQ 中更有效的 INT8 Conv/CASK fusion 和 tactic 组合。

## 4. 已确认的根因

### 4.1 QDQ baseline warm start 实际为空

这是本次审计中最明确的实现问题。

`modelopt/onnx/quantization/qdq_utils.py` 中的 `get_quantized_tensors()` 返回：

```python
dequantize_node.input[0]
```

该名称是 `QuantizeLinear` 的输出，也就是量化后的 tensor 名称，例如：

```text
onnx::Conv_1172_QuantizeLinear_Output
```

但是 `import_qdq_baseline()` 使用这些名称匹配原始图的 insertion-point tensor。原始图中的名称是：

```text
onnx::Conv_1172
```

因此两者无法匹配。

实际日志证明：

- ViT 每次显示导入 40 个 cached schemes，但全部是 `0 Q/DQ points`。
- ResNet 每次显示导入 12 个 cached schemes，但同样全部是 `0 Q/DQ points`。
- QDA 系列实验也出现相同行为。

离线将逻辑改成从 DQ 回溯到 Q，再提取 `QuantizeLinear.input[0]` 后：

- ViT 在源图中的名称匹配从 `0/240` 变成 `240/240`。
- ResNet 从 `0/107` 变成 `106/107`。

因此，目前的 `--autotune_qdq_baseline` 实际并没有将普通 PTQ 的 QDQ 模式作为有效 warm start。QDA 和 integrated-QDQ 实验本质上仍是冷启动随机搜索。

但仅修正 tensor 名称仍不够。将修正后的 tensor 集合重新映射到 pattern scheme 后，只能近似恢复：

- ViT：约 215/240 个 QDQ 点
- ResNet：约 87/107 个 QDQ 点

这说明 pattern-level scheme 本身无法精确表达普通 PTQ 的 edge-level QDQ 拓扑。

### 4.2 AutoTune baseline 不是普通 PTQ

AutoTune workflow 中使用的 baseline 是无 QDQ 的 FP16/FP32 模型，而不是普通 PTQ 模型。

因此，ResNet AutoTune 可以得到类似以下结果：

```text
FP32 baseline: 约 1.33 ms
AutoTune:      约 0.77 ms
speedup:       约 1.7x
```

但普通 PTQ 实际为：

```text
0.299 ms
```

AutoTune 虽然打败了 FP32 baseline，却仍比普通 PTQ 慢两倍以上。

当前流程中：

- 普通 PTQ 最终模型不是 AutoTune 的显式候选。
- AutoTune 没有使用普通 PTQ latency 作为性能下限。
- 没有在 AutoTune 最终模型较慢时自动回退到普通 PTQ。
- 配置中虽然存在 `performance_threshold=1.02`，但没有形成最终模型的性能回退 gate。

所以 AutoTune 的速度没有相对于普通 PTQ 的单调性保证。

### 4.3 AutoTune 绕过了普通 PTQ 的 compiler-friendly 节点选择

不开启 AutoTune 时，`modelopt/onnx/quantization/int8.py` 会执行默认节点选择，包括：

- GEMV 和不适合量化的 Conv 排除
- non-residual Add 处理
- MHA、LayerNorm partition
- CASK/KGEN compiler-fusible partition

开启 AutoTune 后，这套 `_find_nodes_to_quantize()` compiler-friendly 路径会被跳过，转而直接使用 AutoTune 返回的节点集合。

这意味着 `autotune=True` 并不是在普通 PTQ 节点集合上做微调，而是用 AutoTune placement 完全替换普通 PTQ 策略。

ResNet 缺失大量 bottleneck 1×1 Conv weight INT8 路径，是该问题的直接体现。

### 4.4 精确 QDQ edge 被降级为 node-level ORT config

AutoTune 搜索内部使用的是精确 insertion point，能够描述：

```text
tensor -> consumer -> input_index
```

但是 `get_ort_quantization_config()` 会将其压缩成：

```text
nodes_to_quantize
no_quantize_inputs
op_types_to_quantize
```

随后 `quantize_int8()` 从原始 ONNX 重新调用 ORT `quantize_static()`，而不是直接对 `optimized_final.onnx` 做 calibration。

该转换会造成：

1. 被覆盖 edge 的 producer 和 consumer 都可能扩展进节点集合。
2. initializer 没有 producer，无法通过 `no_quantize_inputs` 精确排除。
3. producer 的输出量化会按 op type 扩大，而不是按具体 edge 表达。
4. ORT 根据节点集合重新构造 QDQ，无法严格复现 AutoTune 搜索拓扑。
5. `remove_partial_input_qdq()` 等后处理还可能进一步改变边界 QDQ。

ViT 旧 integrated 实验中搜索模型 122 个 activation QDQ 最终只保留 86 个，是该问题最明显的表现。

## 5. 搜索空间和搜索条件问题

### 5.1 搜索使用占位 scale，最终使用真实 scale

AutoTune 搜索导出 QDQ 模型时使用默认占位 scale `0.1`。

检查模型后发现：

- ViT integrated-QDQ s50 搜索模型的所有 activation scale 基本都是 FP16 表示的 `0.1`。
- 最终模型的 activation scale 有大量不同数值。
- ResNet 搜索模型的 activation scale 同样全部为 `0.1`，最终模型则有约 63 个不同数值。

因此，AutoTune 实际优化的是“等 scale 的人工 QDQ 图”，最终运行的却是“真实校准 scale 的 QDQ 图”。

对于 residual Add、MatMul+Add、concat、requantization 和 reformat，scale 是否相等可能直接影响 TensorRT 能否消除或融合 Q/DQ。普通 PTQ 很快只能证明 calibration 本身不会必然导致慢速，不能证明真实 scale 对 AutoTune 拓扑没有性能影响。

该因素具有较高可能性，但仍需要固定拓扑、仅替换 scale 的 ablation 才能定量确认。

### 5.2 ResNet 搜索精度和最终部署精度不一致

ResNet 原始模型为 FP32。AutoTune 的 QDQ 导出逻辑通过 tensor metadata 推导 DQ dtype；对于已有 dtype 信息的 tensor，会保留原始 FP32 dtype，而不是强制使用 FP16。

因此：

- AutoTune 搜索模型仍然主要是 FP32/QDQ 图。
- 最终 ORT 量化模型会经过 FP16 转换。
- 普通 PTQ 模型也按最终 FP16/INT8 环境构建。

AutoTune 在 FP32/mixed precision 环境下选出的 QDQ placement，不一定适合最终 FP16/INT8 TensorRT engine。

### 5.3 ViT 内部搜索和外部 benchmark builder 配置不一致

AutoTune Python benchmark 使用：

- strongly typed network
- direct I/O
- execute-only median latency

部分 ViT 外部 benchmark 使用 `--fp16` weakly typed builder。

搜索候选排序和最终部署使用的 TensorRT 构建模式不完全一致，可能导致 tactic 和 fusion 排序变化。

不过 ResNet 的内外构建配置更接近，性能回退仍然存在，因此该项属于次要因素，不是总体问题的唯一原因。

### 5.4 insertion-point 过滤不完整

当前 `skip_invalid_insertion_points()` 会过滤部分无效 initializer，但没有完整排除：

- LayerNormalization gamma/beta
- Add bias/constant

ViT 搜索结果实际出现了 LayerNorm 参数 QDQ，最终结果还出现了大量 Add bias/constant QDQ。

文档中“bias 和 normalization 参数会被过滤”的描述，与实际实现和产物并不完全一致。

这些参数 QDQ 可能改变 MatMul+Add、LayerNorm 和 residual fusion。

### 5.5 pattern signature 没有考虑 tensor shape

AutoTune pattern signature 主要包含 operator type 和 attributes，没有把 tensor shape、channel、hidden size 等性能关键维度纳入 signature。

因此，相同算子结构但尺寸不同的 region 可能被迫共享同一量化 scheme。例如：

- 不同通道数的 1×1 Conv
- attention projection 和 MLP MatMul
- 不同 stage 的 ResNet bottleneck

这些 region 在 TensorRT 上的最佳精度和 tactic 可能完全不同。

### 5.6 搜索不是全图全局最优

当前 AutoTune 按 pattern/region 分阶段搜索，并使用随机 mutation：

- 不同 pattern 分开选择局部最优 scheme。
- region 存在重叠时，后续决策可能删除或覆盖之前的 insertion point。
- 没有持续保存并比较所有阶段的全图全局最优 snapshot。
- 没有固定随机种子时，s30、s50、s100 是相互独立的随机实验，并不保证搜索次数越多结果越好。
- 最优方案按原始 latency 最小值选择，没有充分使用测量置信区间或性能阈值。

因此，局部 scheme 最优不等于组合后的最终全图最优。

## 6. 因果关系分级

### 6.1 已确认

1. QDQ baseline tensor 名称提取错误，warm start 实际为空。
2. 普通 PTQ 没有作为 AutoTune 候选和性能下限。
3. AutoTune 会绕过普通 PTQ 的 compiler-friendly 节点选择路径。
4. 精确 edge-level QDQ 会被降级为 node-level ORT 配置，最终拓扑发生变化。
5. ViT 最终模型存在大量 Add bias/constant QDQ，与普通 PTQ 不同。
6. ResNet AutoTune 缺失大量普通 PTQ 中的 Conv weight INT8 路径。
7. 搜索模型使用统一占位 scale，最终模型使用真实非均匀 scale。
8. ResNet 搜索模型和最终模型存在 FP32/FP16 精度环境差异。

### 6.2 高概率但尚未单项定量验证

1. Add bias QDQ 破坏 MatMul+Add/GEMM 或 residual fusion。
2. 缺失的 ResNet 1×1 Conv INT8 路径导致更多 FP16 kernel 和 reformat。
3. 真实非均匀 scale 导致搜索模型中可消除的 QDQ/requantization 在最终模型中无法消除。
4. shape 不敏感的 pattern scheme 导致不同尺寸算子使用了不合适的统一策略。

这些推断与 engine size、QDQ topology 和外部 latency 高度一致，但若要给出每项的毫秒贡献，还需要 TensorRT detailed layer info 或逐项 ablation。

## 7. 根因优先级

按修复优先级排序：

1. **P0：修复 QDQ baseline tensor 提取，确保 warm start 不再是零 QDQ。**
2. **P0：将普通 PTQ 最终模型纳入候选，并增加最终性能回退 gate。**
3. **P0：用真实 calibration 后的最终 ONNX 重新比较候选，而不是仅按占位 scale 搜索模型选优。**
4. **P0/P1：避免通过 node-level ORT config 重建 QDQ，保留 exact edge-level insertion point。**
5. **P1：恢复普通 PTQ 的 compiler-friendly partition，特别是 ResNet Conv/BN/CASK 路径。**
6. **P1：过滤 LayerNorm 参数、Add bias/constant 等不合理 insertion point。**
7. **P1：让搜索和部署使用相同 FP16/INT8 精度及 TensorRT builder flags。**
8. **P1：把 tensor/channel shape 纳入 pattern 分组。**
9. **P2：增加固定随机种子、重复测量和全图最优 snapshot。**

## 8. 建议的修复方案

### 8.1 修复 baseline QDQ tensor 提取

当前逻辑：

```text
DQ.input[0] -> QuantizeLinear output
```

建议改为：

```text
DQ.input[0]
  -> 查找对应 QuantizeLinear producer
  -> 取 QuantizeLinear.input[0]
  -> 得到原始 float tensor
```

同时增加测试：

- 提取出的名称必须存在于原始图 tensor 集合中。
- 导入普通 PTQ baseline 后，至少一个 cached scheme 包含非零 insertion points。
- 对 ViT、ResNet 分别验证 QDQ 覆盖率。

但长期不应只保存 tensor name，应直接保存：

```text
(tensor_name, consumer_node_name, input_index)
```

否则同一个 tensor 有多个 consumer 时仍无法精确恢复拓扑。

### 8.2 把普通 PTQ 作为显式候选和回退方案

推荐流程：

```text
普通 PTQ
    -> calibration
    -> TensorRT benchmark
    -> 作为 candidate-0

AutoTune candidates
    -> exact topology
    -> calibration
    -> 相同 TensorRT 配置 benchmark

若 best AutoTune >= 普通 PTQ * threshold
    -> 返回普通 PTQ
否则
    -> 返回 AutoTune
```

这样才能保证 `autotune=True` 至少不会稳定输出比普通 PTQ 更慢的模型。

### 8.3 对搜索得到的 exact QDQ 图原位 calibration

当前路径是：

```text
AutoTune exact QDQ graph
    -> 转 node-level ORT config
    -> 从原始图重新 quantize_static
    -> 得到不同 QDQ graph
```

更合理的路径是：

```text
AutoTune exact QDQ graph
    -> 收集 calibration statistics
    -> 原位替换 scale/zero-point
    -> 不移动、不新增、不删除 QDQ
```

如果短期仍需使用 ORT quantizer，则 `get_ort_quantization_config()` 至少需要表达：

- 精确 consumer
- 精确 input index
- initializer 是否量化
- 精确 output edge

仅使用 `nodes_to_quantize` 和 `no_quantize_inputs` 无法做到无损交接。

### 8.4 保留 compiler-aware 约束

AutoTune 搜索不应完全取代普通 PTQ 的节点选择，而应以普通 PTQ 结果为基础进行受约束搜索：

- 普通 PTQ placement 作为初始 candidate。
- CASK/KGEN/Conv/BN 等高收益 partition 默认保留。
- AutoTune 只对敏感或存在潜在收益的边界做增删。
- ResNet bottleneck 1×1 Conv 不应在没有明确 benchmark 收益时被批量移出 INT8。

### 8.5 对候选做真实 scale 二次排序

可以采用两阶段策略：

1. 使用占位 scale 快速筛选大量 topology candidates。
2. 对排名靠前的若干候选执行真实 calibration，再使用最终部署配置重新构建 TensorRT engine。
3. 只按第二阶段 latency 选择最终方案。

这样既能控制搜索成本，也能避免占位 scale 对 QDQ elimination 和 fusion 的误导。

## 9. 最小验证实验

### 实验一：验证修正后的 QDQ warm start

1. 修正 `get_quantized_tensors()`。
2. 导入普通 PTQ QDQ baseline。
3. 输出每个 cached scheme 的 insertion-point 数量。
4. 在搜索开始前导出 seed 模型。
5. 比较 seed 与普通 PTQ 的 exact edge topology 和 TensorRT latency。

预期：cached scheme 不再全部为零，但仍会观察到 pattern representation 无法完全恢复 baseline。

### 实验二：隔离 scale 影响

保持 QDQ 拓扑完全不变，只比较：

- 所有 activation scale 为 `0.1`
- 使用真实 calibration scale

如果真实 scale 模型明显变慢，则说明当前 AutoTune 用占位 scale 进行候选排序不可靠。

### 实验三：ViT QDQ ablation

在同一 AutoTune 最终模型上分别测试：

1. 删除 Add bias/constant QDQ。
2. 删除 LayerNorm gamma/beta QDQ。
3. 恢复普通 PTQ 的 Add/GELU、Sqrt、residual activation QDQ。
4. 恢复普通 PTQ 的完整 topology。

逐项比较 engine size、P50 和 TensorRT layer fusion。

### 实验四：ResNet Conv INT8 恢复

以 AutoTune s50 为基础：

1. 恢复缺失的 18 个 Conv weight QDQ。
2. 优先恢复 bottleneck 中的 1×1 reduction/projection Conv。
3. 使用普通 PTQ Conv placement 作为 seed。
4. 比较 engine size、INT8 layer 数量、reformat 数量和 P50。

如果性能显著接近 `0.299 ms`，即可确认 AutoTune 搜索空间丢失 compiler-friendly Conv partition 是 ResNet 回退的主要原因。

### 实验五：TensorRT layer-level 对比

对普通 PTQ、AutoTune 搜索模型和最终模型使用完全相同配置构建 engine，并开启：

```text
--profilingVerbosity=detailed
--dumpLayerInfo
```

重点比较：

- INT8/FP16 layer 数量
- fused Conv、GEMM、LayerNorm 和 attention layer 数量
- reformat、quantize、dequantize、requantize layer 数量
- 各层实际 tactic 和耗时

该实验可以把当前高概率推断进一步落实为逐层定量证据。

## 10. 最终判断

当前 AutoTune 性能下降不能简单归纳为“最终 quantizer 没有完整接收到搜索 QDQ 模式”。完整因果链为：

```text
普通 PTQ baseline QDQ 提取错误
    -> warm start 实际为空
    -> AutoTune 从随机/空 placement 开始搜索
    -> 搜索绕过普通 PTQ compiler-friendly partition
    -> 在占位 scale、部分不同精度和 builder 条件下选优
    -> exact edge QDQ 被压缩成 node-level ORT config
    -> ORT 从原始模型重建另一套 QDQ
    -> calibration、FP16 转换和后处理再次改变最终图
    -> 没有与普通 PTQ 比较和回退
    -> 输出模型可能明显慢于普通 PTQ
```

因此，最重要的修复不是单独增加搜索次数，也不是只修补 `get_ort_quantization_config()`，而是同时完成以下三件事：

1. 修复并精确表达普通 PTQ baseline topology。
2. 将普通 PTQ 作为 AutoTune 的候选和性能下限。
3. 对真实校准后的最终模型使用完全一致的 TensorRT 配置进行最终选择和回退。

做到这三点以后，AutoTune 才能从当前的“替换普通 PTQ 策略的实验性搜索器”，变成真正意义上“以普通 PTQ 为起点、具备性能不回退保证的自动优化器”。
